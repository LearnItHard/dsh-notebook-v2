## 二、逐条根因与证据（都已核实，不是推测）

### R1 · 添加到对话：为什么点了只进剪贴板

**现象**：截图里顶部橙色提示 `已复制到剪贴板（当前挂载点未提供对话桥接）`。

**代码**：`lib/client.js:4679-4706` 的 `cite()`：

```js
const ia = props && props.inputActions
if (ia && typeof ia.appendDraft === "function") { ia.appendDraft(body); return true }
// 兜底 → navigator.clipboard.writeText(body) + 上面那句 notice
```

即：`props.inputActions` 取不到（或没有 `appendDraft`）→ 走剪贴板。

**证据链（四步都做了实测）**：

| # | 事实 | 来源 |
|---|---|---|
| A | `sidebar.right.pane.tab` 槽位 catalog 的 `standardProps` **确实列了** `inputActions: InputActions` | `cordis_inspect_query(client/Slots, root=sidebar.right.pane.tab)` |
| B | 但 `@deepseek-ai/dsh-client-ui-sidebar-right` 的客户端 bundle 里 **0 处** `inputActions` 字样（全 asar 扫描 13903 个文本文件，命中只在 conversation / voice-input / client-runner 的类型目录字符串里） | `asar-scan` 全量扫描 |
| C | 真正能用的参照实现 `dsh-better-sidebar` **完全不碰** `props.inputActions`，它走 **client 服务**：`ctx.get("conversation").input.for(actx)` → 读 `draft` → `input.setDraft(next)` | `dsh-better-sidebar/lib/client-editor.js:49451-49473` |
| D | 宿主 `InputActions` 确实提供 `appendDraft(text)`、`insertReference(ref, span)`（带 `span.draftRev === rev` 的 CAS）、`captureInsertion()` | asar `dsh-client-ui-conversation/lib/client.js` ~14704 / ~15347；voice-input 用 `captureInsertion()` + `insertText()` |

**结论**：A 是「类型目录」，不等于「owner 运行时真给」。侧栏 tab 没有 composer，所以没有 `inputActions`。
**正道是 C**（会话作用域的 `conversation.input`），要文件芯片再用 D 的 `insertReference(ref, captureInsertion())`。

**当前投递格式**（`client.js:5199`）：

```js
cite(`\`\`\`${lang} title="${title}#${label}"\n${selPop.text}\n\`\`\``)
// label = Cell [3]:L4-L8
```

→ 是**纯文本围栏**，所以用户看到的是「一坨文本」，不是文件卡片。

### R4 · 「tools 都没了」不成立

- `lib/index.js:1753`：`tools.map((tool) => ctx.tools.register(tool))`，`lib/tools.js` 里 **28 个** `nb_*` 工具（`nb_new` / `nb_add_cell` / `nb_edit_cell` / `nb_run_cell` …）。
- 实测 `cordis_inspect_query(host/Tool, listTools)`：**28 个 nb_* 全部在可调用清单里**（本会话可见）。
- 插件**没有注册任何 `systemPrompt` section**（grep `systemPrompt|promptSection` 零命中）。
- 所以真问题是**可发现性 + 行为**：模型没有被告知「.ipynb 要走 nb_* 工具」，于是选了它更熟的路（写 `nbformat` 脚本）。截图里它自己也说 "Notebook is valid (16 markdown cells, 0 code cells, nbformat OK)" —— 它是**故意用脚本**造 markdown-only 的 notebook。

**待补证据**：那个 session 的原始记录（`~/.dsh/sessions/.../session.v4.jsonl.zstd` 是多帧 zstd，单帧解压只得到 312 字节）→ 需要在实施时用能读多帧的方式确认它当时看到的工具清单。**但这不阻塞**：工具在，缺的是引导。

### R5 · Markdown 格 Shift+Enter 不渲染 + 下一格自动进编辑态

**两处独立的实现缺陷，同一个根：`mdEditing` 状态与焦点语义。**

1. **Markdown 编辑态复用同一个 CM6 编辑器**（`client.js:3904-3950`）：
   `isDoc && !mdEditing` 才渲染 `MarkdownView`，否则落到 `h(CellEditor, editorProps)`。
2. **Shift-Enter 只跑格、不复位 `mdEditing`**：CM6 keymap（`client.js:2597`）`Shift-Enter → onRunBelow()` → `runBelow()`（`client.js:4287`）只做 `runCell` + `focusCell(下一格)`。
   而「完成」按钮（`client.js:3847-3851`）是 `setMdEditing(false)` **再** `onRunBelow()`。
   → 所以 Shift-Enter 后该格仍是 `mdEditing === true`，**继续显示源码** = 用户看到的「没渲染」。
3. **下一格自动进编辑态**：`runBelow` → `focusCell(target.id)`（`client.js:4295`）→ `focusReq` → CellView 聚焦 CM6。
   Jupyter 语义是 **`run-cell-and-select-next`**：跑完**选中**下一格（命令态），要再按 `Enter` 才进编辑。
   代码注释说这是为早先一条反馈故意加的（「跑完不能接着打下一格」）—— 现在这条与 Jupyter 习惯冲突。

## 三、方案

### R1 · 对话投递 v2（结构化 + 文件卡片）

**通道**（照 `dsh-better-sidebar` 的做法，不用 `props.inputActions`）：

```js
const actx = ctx.sessions.scope(sessionId)
const conversation = ctx.get("conversation")
const input = conversation.input.for(actx)
// 纯文本路径
input.setDraft(splice(currentDraft, text, caret))
// 文件芯片路径（首选，形态更接近用户要的「文件那种形式」）
input.insertReference(ref, input.captureInsertion())
```

**定位格式**（纯函数、可单测）：

| 场景 | 定位串 |
|---|---|
| 代码格选中若干行 | `<nb 相对路径>#Cell[3]:L4-L8` |
| 整格 | `<nb 相对路径>#Cell[3]` |
| 输出 / 报错 | `<nb 相对路径>#Cell[3].output` / `.error` |
| 行号未知（DOM 反查失败） | 只给 `#Cell[3]`，**绝不瞎猜行号** |

- cell 序号 = **1-based 显示序号**（与 UI 左侧 `[ ]` 一致），不是内部 id。
- 行号 = cell 内 **1-based** 行号（与 CM6 gutter 一致）。
- 抽出 `formatNotebookRef({ path, cellIndex, startLine, endLine, kind })` 纯函数 → 进 `test/client-logic.mjs`。

**形态**：优先 `insertReference(ref, span)` 造文件芯片；若 `ref` 形状不支持 notebook 定位（待研究报告确认），退化为
「**芯片（文件）** + 正文结构化围栏」：芯片给「文件身份」，围栏给「cell/行范围 + 代码」。

**验收**：
1. 点「💬 添加到对话」→ 主对话输入框出现内容/芯片，**不再出现剪贴板提示**；
2. 内容带 `#Cell[n]:Lx-Ly`；
3. 非右栏挂载（拿不到会话作用域）时，才允许退回剪贴板，且提示文案要说清「无法桥接，已复制」。

### R2 · 快捷键对齐（等研究报告定稿，先定框架）

引入**命令态 / 编辑态**两个状态（当前完全没有），这是 Jupyter 键位的语义基础：

- 命令态（选中格、蓝色边、按键不输入文本）：`↑/↓` 选格、`Enter` 进编辑、`A` 上插、`B` 下插、`DD` 删、`Z` 撤销删、`Y/M/R` 切类型、`Shift-M` 合并、`Ctrl-Shift-Minus` 拆分、`Ctrl-S` 保存、`L` 行号、`O` 折叠输出。
- 编辑态：`Shift-Enter`（跑并选中下一格）、`Ctrl-Enter`（原地跑）、`Alt-Enter`（跑并下方插入）、`Ctrl-]` / `Ctrl-[` 缩进、`Tab` 补全/缩进、`Ctrl-/` 注释、`Ctrl-D` 删行、`Esc` 回命令态。
- 与宿主冲突的键（`Ctrl-S`、`Ctrl-/`、`Esc`）先做「谁先拿到事件」的实测再定。

（详细清单与冲突矩阵见研究报告，报告落 `docs/research/2026-11-04-jupyter-shortcuts.md`。）

### R3 · AI 双设置

**数据模型**（新键 `nb2.aiPrefs.v2`，自动迁移 v1）：

```js
{
  completion: { enabled: false, provider, model, reasoningEffort },  // ghost / 注释生成代码
  inline:     { provider, model, reasoningEffort }                   // AiBar 改写/解释/修错
}
```

- 迁移：v1 的 `{provider,model,reasoningEffort}` → `inline`；`completion` 继承同模型但 `enabled: false`。
- 补全开关进 `completion.enabled` → **持久化**（修掉「每次重开都关」）。
- UI：工具栏「AI 补全」按钮保留（快捷开关），旁边加齿轮 → 面板两段式设置：`补全` / `改写`，各自 provider + model + 强度 + 「测试」。
- 后端：`/nb2/ai/complete` 取 `completion.*`，`/nb2/ai/stream` 取 `inline.*`；两个端点协议不变。

**验收**：改「补全」的模型不影响「改写」的模型；刷新页面后两者都记住；关掉补全不影响 Mod-K 改写。

---

### R4 · 让模型用 nb_* 工具

1. **host 半注册 `systemPrompt.section`**（现在完全没有）：
   「涉及 `.ipynb` 的创建/编辑/运行，一律用 `nb_*` 工具；**不要**写 `nbformat` 脚本改 ipynb。用户说『新建 notebook / 写个 notebook』→ `nb_new` + `nb_add_cell`。」
   （注意踩坑：section 的 `text()` 拿不到 session/cwd，只能写静态文本。）
2. **工具描述补「何时用」**：`nb_new` 明确「用户要新建 notebook 时先调它」；`nb_add_cell` 明确「先写 markdown 方案再写代码时，用 `cellType: "markdown"` 连续调用」。
3. **降低脚本动机**：`nb_add_cell` 支持一次传多格（`cells: [...]`），避免「16 个 markdown 格 → 写脚本更快」的直觉。

**验收**：新 session 说「在这个目录新建一个 notebook，先写方案文字」→ 轨迹里出现 `nb_new` / `nb_add_cell`，**没有** `nbformat` 脚本。

---

### R5 · Markdown 提交 + 命令态（改法已明确）

1. **`mdEditing` 复位**：CellView 里把 `editorProps.onRunBelow` 包一层：
   ```js
   onRunBelow: () => { if (isDoc) setMdEditing(false); onRunBelow() }
   ```
   同理 `Ctrl-Enter`（原地跑）也要渲染。
2. **`runBelow` 增加焦点模式**：
   ```js
   runBelow(cellId, { mode: "select" | "focus" })   // 默认 "select"
   ```
   `select` → 只 `setSelected(next)`（命令态，不聚焦编辑器）；`focus` → 现在的 `focusCell`。
3. **设置项**（跟着 R3 的设置面板一起）：`Shift-Enter 后进入下一格编辑态`（默认**关**，即 Jupyter 语义）。

**验收**：Markdown 格 Shift+Enter → 立刻渲染成排版视图 + 下一格被选中（无光标）；再按 `Enter` 才进编辑。

## 五、待确认的决策点（影响行为，先问再动）

1. **R5 默认语义**：Shift-Enter 后下一格 = **命令态选中**（Jupyter 默认，推荐）/ 保持现在的**自动进编辑态** / 做成设置项默认关（推荐方案：设置项 + 默认命令态）。
2. **R3 拆分粒度**：只拆「开关 + 模型」两套（推荐、最小可用）/ 连「触发延迟、最大续写行数、是否只在注释行触发」也各自可配（更重）。
3. **R1 芯片形态**：若 `ref` 不支持 notebook 定位 → 「文件芯片 + 结构化围栏正文」（推荐）/ 只发结构化围栏纯文本（最简单、与 better-sidebar 一致）。
4. **R4 是否允许改模型行为**：加 `systemPrompt` 段会**改变所有会话**里模型对 `.ipynb` 的处理方式（推荐加，但需明确接受）。

## 六、风险与回滚

- **R1 通道换血**：`ctx.get("conversation")` 若在非右栏挂载下也拿不到 → 必须保留剪贴板兜底 + 明确文案；`setDraft` 是「整串替换」，**必须基于当前 draft 做 splice**，不能直接覆盖（否则吞掉用户已输入内容）。
- **R3 迁移**：v1 → v2 迁移只做一次；迁移失败一律回落默认值，**不允许抛到 UI**。
- **R2 键位**：`Ctrl-S` / `Ctrl-/` / `Esc` 与宿主争抢 → 每加一个键都要有「宿主是否先消费」的实测记录。
- **R5 焦点语义**：命令态没有光标时，`Enter` / 方向键必须由面板级分发器（`decideCellKey`）接住，否则「选中了但按什么都没反应」——这正是之前踩过的坑（焦点掉到 body）。
- 回滚：所有改动集中在 `lib/client.js` + `lib/index.js`；`git` 未跟踪该包，**改动前先 `cp` 一份 `lib/client.js.bak-<date>`**。

## 九、AI 自动补全修改计划（据开源调研，2026-11-04）

> 调研报告：`docs/research/2026-11-04-ai-completion-survey.md`（395 行，3 张表 + NES 专段）

### 一句话结论

开源实现的差距**不在「会不会调模型」**，而在四件工程事：
① 输入即取消 + 前缀缓存（延迟/成本）② 局部接受 + 多候选（交互）
③ 结构化上下文（FIM 拼接 / 跨 cell / kernel 变量）④ 上下文过滤器（**什么时候不发请求**）。
我们此前 ①②④ 基本空缺，③ 只做了「前 3 格源码」。

### 已实施（本轮，测试全绿）

| # | 能力 | 做法 | 参考 |
|---|---|---|---|
| P0-1 | **在途请求即时取消** | `schedule()` 入口 abort 上一个 `inflight`；此前只在编辑器销毁时 abort → 每敲一个字符白烧一次 1–2s 的 token | Continue `CompletionProvider` |
| P0-2 | **前缀缓存（LRU 64）** | 键 = `光标位置 + 文档全文`；命中直接 dispatch 幽灵文本，0 网络延迟；退格/改回来立即可见 | Continue `AutocompleteLruCache` |
| P0-3 | **按词接受** | `acceptWord` 原为**死代码**（0 处调用），现绑 `Ctrl-→` + `Alt-f`；吃掉下一个词，其余继续留在幽灵态 | VS Code `acceptNextWord` / Cursor `Cmd-→` |

## 十、快捷键架构：命令注册表 + 键位表（2026-11-04，用户提议后重构）

### 用户的提议（原话意译）

> 「快捷键这部分，是不是要先把各个功能的 API 都预留出来，然后再写个脚本把快捷键和 API 联通起来，是不是更优雅一点？」

**是对的**，而且这正是 Jupyter / VS Code 的标准做法（command registry + keybinding contribution）。
重构前的实际问题是：同一条动作被**四处**各写一遍闭包 ——
面板快捷键、工具栏按钮、右键菜单、CM6 keymap。改一处忘三处是必然结果，
`acceptWord` 写好了却从来没接线（死代码）就是这么产生的。

### 重构后的三层

| 层 | 位置 | 职责 | 可测 |
|---|---|---|---|
| **`COMMANDS`** | 模块级纯数据 | 命令 id → `{ label, hint }`（动作的**元数据**，也是 UI 文案的唯一来源） | ✅ 纯数据 |
| **`KEYBINDINGS`** | 模块级纯数据 | 键位 → 命令 id（`context: "command" \| "global"`、`twoStep`）。**只有这张表知道快捷键** | ✅ 纯数据 |
| **`commandsRef.current`** | 面板内，每帧重建 | 命令 id → 真正执行的闭包（要 state，只能在组件里建） | 间接（源码级断言） |

分发链路：`keydown` → `decideCommandKey(state)`（纯函数，键位表 → 命令 id）
→ `commandsRef.current[command]`（执行）。找不到执行体时**明喊**「未实现的命令」，
不再静默变成「按了没反应」。

### 为什么用 `commandsRef` 而不是 `useMemo(deps)`

执行表引用了 `moveCellTo` / `mergeBelow` / `citeCellRef` 等**在后面才声明**的符号。
把它们写进依赖数组会在首次渲染就 TDZ 崩 —— 本仓库已经踩过一次
（`Cannot access 'citeCell' before initialization`，冒烟测试抓到的）。
ref 每帧重赋值既避开 TDZ，又保证闭包永远是最新 state。

### 消费者已统一

- **面板快捷键**：键位表驱动（`decideCommandKey`）。
- **右键菜单**：菜单项只写命令 id，`label`/`hint` 从 `COMMANDS` 取、执行从 `commandsRef` 取
  → 菜单上显示的快捷键**永远等于**真实绑定。
- **工具栏按钮**：仍是各自闭包（低频、且带视觉状态），**待迁移**；
  迁移时只需把 onClick 换成 `commandsRef.current[id]`。
- **CM6 keymap**（编辑器内部：Tab / Ctrl-→ / Alt-\ / Mod-K）：仍由 `buildExtensions` 持有，
  因为需要 view 级 API（dispatch、选区坐标）。它们的 hint 已登记进 `COMMANDS`，
  并有测试断言「这 4 条是唯一允许没有面板执行体的命令」。

### 护栏（都是自动化的）

1. 每条键位指向的命令必须在 `COMMANDS` 里有元数据；
2. 同一 context 下不允许重复键位（否则先匹配者赢，另一个静默失效）；
3. 除 4 条编辑器内部命令外，**每个命令都必须有执行体**（防死代码）；
4. 源码级断言：不许再出现 `cmd.action` 分支（防止退回旧写法）；
5. Jupyter P0 键位覆盖清单（A/B/D/Z/Y/M/R/↑/↓/Enter/Esc/Mod-S/Shift-M）逐条断言。

### 怎么加东西（下次照做）

- **加一个快捷键**：`KEYBINDINGS` 加一行 → 跑测试（缺命令立刻红）。
- **加一个动作**：`COMMANDS` 一条 + `commandsRef.current` 一条 → 菜单/按钮直接引用 id。
