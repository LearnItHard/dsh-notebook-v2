## 1. 「为什么不直接把 VS Code 的 Jupyter 插件搬过来」

这是本轮最值得先讲清楚的一条，因为它决定后面所有取舍。

### 1.1 为什么搬不动（不是不想）

| vscode-jupyter 的层 | 依赖 | 能否搬 |
|---|---|---|
| 扩展激活 / 命令 / 状态栏 | VS Code **extension host** + `vscode` 模块 | ❌ 没有扩展宿主 |
| cell 交互、焦点、工具栏、虚拟滚动 | VS Code **Notebook API**（`vscode.NotebookCellData`、`NotebookCellList`、`CellFocusMode`、`INotebookExecutionStateService`） | ❌ 这是 VS Code workbench 内部实现，不是插件代码 |
| 编辑器 | **Monaco**（`CodeCell.setModel`、编辑器池、`CodeCellRenderer.renderTemplate`） | ❌ 我们用的是 CM6（且 Monaco 101MB + worker，见既有决策） |
| 输出渲染 | `vscode-notebook-renderer` API + **webview** 隔离 | ❌ 需要 VS Code 的 renderer 通信层 |
| 内核协议 | `jupyterlab/services`-style 纯 TS + `nbformat` | ✅ **我们已经等价拥有**（sidecar 走 jupyter_client 的 Jupyter messaging） |
| 输出 MIME 处理 / nbformat 归一 | 纯 TS 逻辑（`src/kernels/execution/helpers.ts`） | ✅ 语义已抄（`translateStreamOutput` → 我们的 stream 合并、`raises-exception` 继续） |

**一句话**：vscode-jupyter 里「用户看得见的那 80%」是 VS Code 平台代码（workbench + Monaco + webview renderer），插件本体是接线员。搬插件 = 搬一具没有骨架的身体。

### 1.2 真正该复用的三样东西（本轮就用）

1. **协议层**：已经是标准 Jupyter messaging（不发愁）。
2. **渲染层**：`marked` + `dompurify` + `katex`（JupyterLab 的 rendermime 其实也是这条链路的同族：`markdown-it` + `DOMPurify` + KaTeX，只是它绑 `@lumino/*`）。
3. **符号层**：VS Code 的 Outline 来自 LSP `documentSymbol`；我们没有 LSP，但 `@lezer/python` 是货真价实的 Python 语法树，**已经在包里**，比正则准、比 LSP 轻。

### 1.3 为什么不引 JupyterLab 的 rendermime
`@jupyterlab/rendermime` 与其 markdown 渲染器依赖 `@lumino/widgets` / `@jupyterlab/apputils` 的 DI 容器，
塞进 DSH 客户端插件（只能 `require` 白名单模块）需要连带一套 Lumino widget 生命周期；而它内部用的就是
`markdown-it` + `DOMPurify` + `katex`。**直接用它依赖的那三件，比搬它自己便宜一个数量级。**

### 1.4 边界（明确不做）
ipywidgets（`jupyter-js-widgets` 需要 comm + 前端模型，独立工程）、调试器、Monaco、LSP 级类型诊断。

## 3. 文件改动清单（预估）

### 宿主半 `lib/index.js`（+~180 行）
- `defaultCwdFor(sid)`：`agents.get(sid)` → `workingDirectory.get(agent.session)` → `workingDirectory.defaultDirectory` → `sandboxPolicy.workspaceRoot` → `process.cwd()`；**替换现有 `workspaceRoot()` 的三处调用点（263/516/657/951）**，并保留 `workspaceRoot()` 作为最后兜底。

| 风险 | 缓解 |

## 7. 事实核查与原型证据（2026-11-04 本条线亲自实测，不是推断）

| # | 计划里的假设 | 实测结果 | 对计划的影响 |
|---|---|---|---|
| 7.1 | 需要 `npm i marked/dompurify` | **不需要联网**：`~/.dsh/profiles/desktop/.nb2-build/node_modules` 已有 `marked@18.1.3`、`dompurify@3.4.17`、`katex@0.16.11`、`marked-katex-extension`；profile 的 `node_modules` 里也有一份，且 `@lezer/python` 可解析 | 构建脚本按「.nb2-build 优先 → profile 兜底」解析，缺依赖必须硬失败 |
| 7.2 | KaTeX 只有 JS 没有 CSS | 确认：`grep -c 'katex.min.css\|@font-face' lib/cm-vendor.js lib/client.js` = **0 / 0**；但 `renderToString` 已在 vendor 里（katex JS 早打进去了） | 只缺 CSS + 字体。`katex.min.css` 23,335B；woff2 20 个、254KB → base64 约 348KB |
| 7.3 | md 与公式要两套处理 | 实测 `marked.use(markedKatexExtension({throwOnError:false}))` 一次产出 `<table>`、`<input type=checkbox>`、`<span class=katex>` | 一个 marked 实例同时解决 GFM + 数学，**不再自己写 `$$` 正则** |

| 7.5 | 默认目录取 `agents.get(sid)` → `workingDirectory.get(agent.session)` | 宿主服务签名核对无误：`workingDirectory.get(session: Session): string`、`readonly defaultDirectory: string`、`agents.get(id: SessionId): Agent \| undefined` 全存在 | 取法可行；另发现 `directoryPickerController` 有 `@Remote list(path)/pick()`，留作后续增强，本轮不依赖 |
| 7.6 | 把 markdown 拆到 `lib/md.js`（原 §3 的测试建议） | **作废**：`lib/client.js` 是 `__ModuleLoader__.load({id, factory})` 的自包含 CJS 工厂，**不能 import 兄弟文件**；测试壳（`test/client-logic.mjs`）用 React 桩加载它 | md/outline 纯逻辑**内联在 client.js**，经 `__internals` 暴露；测试用 `CM` 桩注入 marked/lezer。**不新增 `lib/md.js`** |
| 7.7 | 基线是否健康 | `node test/all.mjs` **全绿**（28 个 `nb_*` 工具、多标签、执行/中断/重启、变量留存、语义等价读写） | 改动必须保持这套绿 |
| 7.8 | 改完怎么生效 | `/nb2/health` → `{ok:true, version:"0.1.0"}`；profile 的 `node_modules/dsh-notebook-v2` 是**指向本仓库的 symlink** | 宿主半：`plugin_manager set_plugin` 重挂即生效；客户端半：刷新页面 |

补充实测（原计划没写、但影响实现）：

- 宿主路由是**单条 prefix `/nb2` + 手动分发**：`route = url.pathname.replace(/^\/nb2\/?/, "")`，
  `vendor.js` 在 `readJson` 之前特殊返回，`sid = body.sid || url.searchParams.get("sid") || "default"`。
  新路由就挂在这个 handler 里，不新注册 route。
- `test/_load.mjs` 把 `lib/*.js` **逐个复制**到临时目录再加载 → 新模块若带裸 import（`marked`）会在临时目录解析失败。
  这是 7.6 判定的直接原因，也约束宿主半**不得**在运行时 import third-party 包。

### 9.2 采纳的建议改

- **katex 字体不全量 base64**：`katex.min.css` 里有 **60 个 `url()`**（woff2/woff/ttf 三份）。改为只保留 woff2（20 个，约 254KB），改写为绝对路径 `/nb2/fonts/X.woff2`，`immutable` 缓存，浏览器按需惰性下载（典型文档只用 8 个）。
- **分发器必须 `if (e.defaultPrevented) return`**：`2899-2913` 的 AI 条在 window capture 只 `preventDefault` 不 `stopPropagation`，否则会「接受 AI 改动」+「把旧代码又跑一遍」双触发。
- **不新增 Ctrl-Shift-Enter**：VS Code 真实键位是 Shift-Enter（跑+下移）/ Ctrl-Enter（原地）/ Alt-Enter（跑+下方插入），Alt-Enter 已在 `1025` 绑好。
- **`@lezer/python` 不写进 `.nb2-build/package.json`**：让它上溯用 profile 那份（与 `lang-python@6.2.1` 共用），否则打出第二份 lezer。
- **`CM.DOMPurify` 可能是工厂**：必须 `typeof .sanitize === "function"` 守卫，不满足就回落 `markdownLite`（纯 `h()` 构造，天然安全），绝不把未消毒 HTML 交给两处 `dangerouslySetInnerHTML`。
- **`marked.parse` 按 source 缓存**（上限 ~200）+ 超大 md 先显源码，避免 App 级重绘卡主线程。
- **测试可测性**：抽 `decideCellKey` / `nextRunTarget` / `renderMarkdown` / `rewriteImgSrc` / `buildOutlineV2` 进 `__internals`（ReactStub 的 `useState` 无状态、`useEffect` 空实现，组件树里测不到键盘与聚焦）。

### 9.3 新增 P0（评审指出的遗漏）

### 9.6 关于「为什么不直接把 VS Code 的 Jupyter 插件搬过来」（补强）

用户原话问的就是这条，§1 只论证了 JupyterLab rendermime，漏了最直接的一问：**能不能直接复用 `dsh-better-sidebar` 的 markdown 渲染器**？
评审核实：**不能**。它的渲染器在它自己的 `lib/client.js` 里、没有挂到 `window`，而 DSH 客户端插件是**隔离的自包含 CJS 工厂**（`client.js:135-137`，测试桩对非 `react` 直接抛错），跨包 import 不可能。
所以只剩两条路：抄它的实现思路（我们这轮走的：marked + DOMPurify + KaTeX 三件套）或自己重写。这也反过来印证 §1.1 的结论：vscode-jupyter 里用户看得见的 80% 是 VS Code 平台代码，不是可搬的插件代码。
